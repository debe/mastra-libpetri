# Divergences from Mastra

Every Mastra behaviour this engine does not reproduce is listed here with its classification.
Nothing is skipped silently.

**Classifications.** `abandoned (cause removed)` — the behaviour existed to work around
something this model does not have. `abandoned (defect)` — reproducing it would propagate a
bug. `out of scope` — real behaviour, deliberately not covered by this engine. `replaced` — the
same intent, a different mechanism. `addition` — capability Mastra's engine does not have.

**Statuses.** `proposed` — reasoned from source only. `designed` — the mechanism is observed by
a harness. `refused (M<n>)` — the adapter throws rather than compiling something it would get
wrong, so the divergence is loud at build time. `open (M<n>)` — known wrong, compiled anyway,
not yet fixed; this is the status that must not accumulate. `fixed (M<n>)` — closed in that
milestone.

**Rows 7 onward were established in M1 by reading Mastra's own source** — `@mastra/core@1.67.0`,
recovered from the sourcemaps the package publishes (`scripts/bootstrap-mastra.sh --dist`), so
every citation below resolves to a real line rather than to a planning-time reading. A `refused`
row is a deliberate choice: compiling a wrong answer is worse than refusing to compile.

| # | Mastra behaviour | Classification | Rationale | Status |
|---|---|---|---|---|
| 1 | `.sleep(ms)` resumes with its remaining interval after a suspend | replaced | [CORE-073] restores a marking with every clock fresh, so a restored `.sleep(ms)` re-waits in full. Sound because restores are occasional and `Delayed` is a lower bound; the compiler emits no hard timing on a path that can cross a restore. Unsound for a scheduler that parks and resumes routinely — revisit if Mastra gains one. A per-run or literal `.sleepUntil`, and a per-run `.sleep`, wait inside an action, so they are in flight and cannot be checkpointed mid-wait; neither can Mastra's | proposed |
| 2 | Cron-scheduled workflows | out of scope | Declaring `schedule` forces Mastra's evented engine, so a scheduled workflow never reaches this engine | proposed |
| 3 | `.waitForEvent()` | out of scope | Removed upstream; throws `WORKFLOW_WAIT_FOR_EVENT_REMOVED`. Suspend/resume is the mechanism | proposed |
| 4 | Total execution order across independent steps | abandoned (cause removed) | The net produces a partial order. The differential harness requires it to be a *weakening* of Mastra's total order, never a reordering — an unattributed ordering difference is a finding | proposed |
| 5 | `.parallel()` fan-out is unbounded | addition | A `concurrency` annotation compiles to a permit place. Layer 2: a workflow carrying it still runs correctly under `DefaultExecutionEngine`, merely unbounded. The rebuilt gadget is unbounded like `Promise.all`; nothing added yet | proposed |
| 6 | Step timeouts are not virtualized under an injected clock | out of scope (upstream) | `Out.Timeout` still elapses on a real `setTimeout`; only its recovery tokens follow the epoch clock. Reported upstream. Keep timeout values small in timed tests | proposed |
| 7 | `.map()` entries (`{type:'mapping'}`) | replaced | Compiled as a step with `source: 'mapping'`; `StepCall` carries `initData` and `getStepResult` for any earlier step. Parity also needs the M2 runner to translate: `RunView.getStepResult` returns a `StepOutcome` where Mastra's returns output-or-null (`handlers/step.ts:179-193`) | fixed (M1) |
| 8 | `.sleep(fn)` / `.sleepUntil(fn)` — a wait computed per run | replaced | `{perRun: true}`, resolved through `StepRunner.resolveWait` and waited on the run's clock inside the action. `structuralHash` hashes `perRun`, not a value | fixed (M1) |
| 9 | A wait above 2147483647ms (~24.9 days), including `Infinity` | abandoned (defect) | Mastra waits with a bare `setTimeout` (`utils.ts:230-251`); Node resets any delay above the timer maximum to ~1ms. A literal `.sleep` or a `retryConfig.delay` past it is refused by the adapter; a per-run wait or a literal `.sleepUntil` whose instant is further away than that when reached fails the run naming the ceiling | refused (M1) |
| 10 | `.sleepUntil(new Date(<unparseable>))` | out of scope | For a **literal** Invalid Date, Mastra rejects the run: `date.toISOString()` throws `RangeError` while naming the sleep's span (`handlers/sleep.ts:206`). Refused by the adapter. A **per-run** `NaN` instant (Mastra's ~1ms wake, `:256`) fails the run naming the value | refused (M1) |
| 11 | Step-level `retries` and workflow-level `retryConfig.attempts` | replaced | Resolved as Mastra does, `step.retries ?? retryConfig.attempts ?? 0` (`handlers/step.ts:314`). **Unrolled**: one transition per attempt, the retry wait `delayed(d)`; the ceiling is structure, not a counter. `MastraNonRetryableError` short-circuits, a TripWire is retried, only the last attempt is recorded. Above `MAX_RETRIES` (100) see row 24 | fixed (M1) |
| 12 | An empty `.parallel([])` or `.branch([])` | replaced | One pass-through transition depositing `{}`, as Mastra's reduce over no results gives. All three properties proven for it as a sole and as a middle entry | fixed (M1) |
| 13 | `.dowhile()` / `.dountil()` with no iteration bound | addition | Mastra's loop has no cap (`handlers/control-flow.ts:739,901`). `iterationBound` is ours and required explicitly, in [1, 100000]. Exceeding it fails the run naming the bound. The bound stops the loop **at runtime by construction** — the budget has one producer and every iteration spends one token — and that is pinned by a structural test, **not by a proof**: the verified properties range over quiescent markings only ([VER-002]), so an endless cycle would violate none of them | refused (M1) |
| 14 | `.foreach(step, {concurrency: fn})` — a per-run resolver | out of scope | Items in flight are fixed when the workflow is compiled, and one compiled net serves every run | refused (M1) |
| 15 | A `.foreach()` whose static `concurrency` is mutated between build and execution | out of scope | Mastra keeps the caller's options object by reference. The adapter reads it live, so adapting inside every `execute()` closes this in M2 | open (M2) |
| 16 | A `StepFlowEntry` type, or a value outside Mastra's declared types, this engine has not seen | out of scope | Refused naming the tag: an unknown entry type, an unknown `loopType`, a non-number duration or delay, a non-Date `sleepUntil` date, control flow in an arm or body | refused (M1) |
| 17 | The record a `.branch()` / `.parallel()` hands the **next** entry | replaced | Not last: every declared arm read from the step results, so a skipped arm is present as `undefined` or as a stale earlier output (`default.ts:1141-1149`). Last: only the arms that ran in this block and succeeded (`handlers/control-flow.ts:286-295,616-624`). Both shapes tested, the stale case included | fixed (M1) |
| 18 | `.foreach()` stops dispatching after the first non-success item | replaced | Every non-success settle resets the cursor (`queue.kill()`), and every start is inhibited by the other lanes' non-success places; in-flight items finish. `mutualExclusion(cursor, faults)` proven at c=2 and c=3, and removing the reset flips it. The start inhibitors are pinned by executor tests only | fixed (M1) |
| 19 | `suspended`, `bailed`, `paused` step outcomes, and tripwire | replaced | Five outcomes (tripwire is a field of `failed`, as in Mastra), each routed to an exit the enclosing context chooses ([ADR 0003]). Residuals are rows 33–37 | fixed (M1) |
| 20 | Which error is reported when several arms fail | replaced | The lowest arm index, as `results.find` over index-aligned results (`handlers/control-flow.ts:267,596`), via `all(errSeen)`. Duplicate arm ids are row 33 | fixed (M1) |
| 21 | A `.branch()` condition that throws | replaced | Reproduced by contract: the runner reports a throwing condition as falsy, as Mastra's `evaluateCondition` does (`handlers/control-flow.ts:467-492`). The block fails only when `selectBranches` itself throws, is missing, or returns a bad index. Holds once the M2 runner catches each condition separately | open (M2) |
| 22 | A `.foreach()` over input that is not an array | replaced | Reproduced where Mastra is defined: a string iterates its code units, an array-like by length, a non-positive length gives `[]` (`handlers/control-flow.ts:1050,1228,1272`). `null`/`undefined` fail the run where Mastra's `start()` rejects (row 26) | designed |
| 23 | A nested workflow's internal steps | replaced | `source: 'workflow'` (`step.component === 'WORKFLOW'`, `step-entry.ts:61-70`), run opaquely as one step; its `paused` outcome is modelled end to end. Its internals are outside every proof until M8 compiles it as a subnet | proposed |
| 24 | A workflow Mastra runs whose net this engine cannot | out of scope (upstream) | Retries above `MAX_RETRIES` (100) and `.foreach()` concurrency above `MAX_FOREACH_LANES` (256) are refused by the adapter; a net above `MAX_NET_PLACES` (4096) is refused by `compile()`. The last guards a libpetri defect: `PrecompiledNet` kept a single-word index in an `Int8Array`, so place ids from 4096 up wrapped negative — a synchronous spin no timeout reaches on an input arc, an ignored inhibitor on an inhibitor arc. Root-caused and fixed upstream; the guard lifts with the release that carries it | refused (M1) |
| 25 | A non-whole or negative retry count | out of scope | Refused conservatively. Mastra's loop is well-defined on the success path for some of these (a huge count succeeds on the attempt that succeeds), so this is caution, not an absence of behaviour | refused (M1) |
| 26 | `run.start()` rejects with no run status | replaced | A throwing loop condition (`handlers/control-flow.ts:835`), a throwing `.sleep(fn)` (`handlers/sleep.ts:83-128`) and `.foreach()` over `null` reject in Mastra; we fail the run instead, with the failure recorded. The differential harness must pair the two | designed |
| 27 | A loop whose body id already has a step result | out of scope | Mastra starts from that result's payload and continues `metadata.iterationCount` (`handlers/control-flow.ts:727-734`), so `.then(s).dowhile(s)` feeds `s`'s input. We start from the incoming value at iteration 1. Needs the step-result store to carry payload and iteration count | open (M2) |
| 28 | Cancellation inside control flow | out of scope | Mastra returns `canceled` from a block's precedence ladder (`handlers/control-flow.ts:278-281,596-625`), between loop iterations (`:742-753,807-818,889-900`) and at foreach dispatch with partial results (`:1160-1172`). There is no cancel path in the contract yet; CLAUDE.md requires it structural | open (M2) |
| 29 | Context given to conditions beyond `RunView` | out of scope | Loop conditions also get state, a no-op bail, abort, a writer and a run count (`handlers/control-flow.ts:836-874`); branch conditions get state, request context and abort (`:419-455`). The M2 runner supplies these | open (M2) |
| 30 | Loop, conditional and foreach spans and progress events | out of scope | `WORKFLOW_LOOP` / `WORKFLOW_CONDITIONAL` spans with `truthyIndexes`, and per-item foreach progress (`handlers/control-flow.ts:373-392,1066-1084`). Streaming is M5 | open (M5) |
| 31 | The foreach await window before `killQueue()` | abandoned (defect) | Mastra awaits a progress publish before killing the queue (`:1126-1141`), so a sibling finishing in that window can release one more item. We stop dispatch as soon as the outcome exists | designed |
| 32 | Per-item foreach context | replaced | The runner sees a lane path and no `foreachIndex`, where Mastra runs every item at the foreach's path with `foreachIndex` (`handlers/control-flow.ts:1101`; `handlers/step.ts:109,152-154,406`) — no per-item nested run id or resume data | open (M2) |
| 33 | Duplicate step ids across arms | replaced | Several failures: ranked by the id's first arm, ties by arrival, so the error and even the status (tripwire vs failed) can differ from Mastra's lowest index. Several suspensions: we report the lowest index where Mastra's snapshot is last-in-time per id. Closes when failures carry their path | open (M2) |
| 34 | Several arms of one block suspend | replaced | Only the lowest-index suspension reaches `wf.suspended`; the others are in the step results. Mastra lists every suspended step and path. The codec derives them from step results plus the `NetMap` | open (M4) |
| 35 | Foreach suspend/resume bookkeeping | out of scope | `__workflow_meta.{foreachIndex, foreachOutput, resumeLabels}`, replay-skip of succeeded items, the nested run id array (`handlers/control-flow.ts:1366,1442-1450,1193`) | open (M4) |
| 36 | A foreach failure loses `nonRetryable` | replaced | Mastra keeps it on the aggregate failure (`:1360-1369`); `FailureToken` does not carry it yet | open (M2) |
| 37 | A sleep's `waiting` step result | out of scope | Mastra writes `{status:'waiting'}` before sleeping (`handlers/entry.ts:605`). We record nothing until the wait succeeds | open (M2) |
| 38 | A zero or negative wait takes one timer tick | replaced | Modelled as no wait, for `.sleep` and for a negative `retryConfig.delay` | proposed |
| 39 | A stored `failed` result for a truthy branch arm | abandoned (cause removed) | Mastra returns it without running the arm (`:552-553`); reachable only through carried-in or restart state. We run the arm | proposed |
| 40 | `.parallel()` / `.branch()` under `perStep`, `timeTravel` or `restart` | out of scope | Partial arm start and arm narrowing (`handlers/control-flow.ts:188-213,499-553`). The engine must refuse these `execute()` parameters | open (M2) |
| 41 | The same `Step` object twice in one `.branch()` | abandoned (defect) | `steps.indexOf` gives both arms the first arm's path (`:569`). We use the true index | proposed |
| 42 | An arm whose step id is `__proto__` | abandoned (defect) | Mastra's reduce assigns through the prototype setter and loses the arm (`:290,618-620`; `default.ts:1143-1145`). We keep it as an own key | designed |
| 43 | Resuming inside a `.parallel()` / `.branch()` | out of scope | `resumePath` re-entry and `buildResumedBlockResult` (`handlers/entry.ts:354-509`) | open (M4) |
| 44 | Mastra's retry backoff cannot be aborted | addition | A bare `setTimeout` (`default.ts:456-458`). Once structural cancellation lands, a pending retry wait is interruptible | proposed |
