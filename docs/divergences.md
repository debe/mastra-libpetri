# Divergences from Mastra

Every Mastra behaviour this engine does not reproduce is listed here with its classification.
Nothing is skipped silently.

**Classifications.** `abandoned (cause removed)` — the behaviour existed to work around
something this model does not have. `abandoned (defect)` — reproducing it would propagate a
bug. `out of scope` — real behaviour, deliberately not covered by this engine. `replaced` — the
same intent, a different mechanism. `addition` — capability Mastra's engine does not have.

**Statuses.** `proposed` — reasoned from source only. `designed` — the mechanism is observed by
a harness. `refused (M<n>)` — the adapter throws rather than compiling something it would get
wrong, so the divergence is loud at build time. `open (M<n>)` — known wrong, compiled anyway,
not yet fixed; this is the status that must not accumulate. `fixed (M<n>)` — closed in that
milestone.

**Rows 7 onward were established in M1 by reading Mastra's own source** — `@mastra/core@1.67.0`,
recovered from the sourcemaps the package publishes (`scripts/bootstrap-mastra.sh --dist`), so
every citation below resolves to a real line rather than to a planning-time reading. A `refused`
row is a deliberate choice: compiling a wrong answer is worse than refusing to compile.

| # | Mastra behaviour | Classification | Rationale | Status |
|---|---|---|---|---|
| 1 | `.sleep(ms)` resumes with its remaining interval after a suspend | replaced | [CORE-073] restores a marking with every clock fresh, so a restored `.sleep(ms)` re-waits in full. Sound because restores are occasional and `Delayed` is a lower bound; the compiler emits no hard timing on a path that can cross a restore. Unsound for a scheduler that parks and resumes routinely — revisit if Mastra gains one. A per-run or literal `.sleepUntil`, and a per-run `.sleep`, wait inside an action, so they are in flight and cannot be checkpointed mid-wait; neither can Mastra's | proposed |
| 2 | Cron-scheduled workflows | out of scope | Declaring `schedule` forces Mastra's evented engine, so a scheduled workflow never reaches this engine. `init()`'s `createWorkflow` refuses `schedule` by type (`never`) and at runtime (TypeError) | refused (M2) |
| 3 | `.waitForEvent()` | out of scope | Removed upstream; throws `WORKFLOW_WAIT_FOR_EVENT_REMOVED`. Suspend/resume is the mechanism | proposed |
| 4 | Total execution order across independent steps | abandoned (cause removed) | The net produces a partial order. Only pairs a fixture declares `independent` may be reported as weakened. At k = 1 the corpus declares none and shows 0 reversed, 0 inverted and 0 weakened pairs (`tests/conformance/differential.test.ts`); k > 1 is M3 | designed |
| 5 | `.parallel()` fan-out is unbounded | addition | A `concurrency` annotation compiles to a permit place. Layer 2: a workflow carrying it still runs correctly under `DefaultExecutionEngine`, merely unbounded. The rebuilt gadget is unbounded like `Promise.all`; nothing added yet | proposed |

| 11 | Step-level `retries` and workflow-level `retryConfig.attempts` | replaced | Resolved as Mastra does, `step.retries ?? retryConfig.attempts ?? 0` (`handlers/step.ts:314`). **Unrolled**: one transition per attempt, the retry wait `delayed(d)`; the ceiling is structure, not a counter. `MastraNonRetryableError` short-circuits, a TripWire is retried, only the last attempt is recorded. | 12 | An empty `.parallel([])` or `.branch([])` | replaced | One pass-through transition depositing `{}`, as Mastra's reduce over no results gives. All three properties proven for it as a sole and as a middle entry | fixed (M1) |
| 13 | `.dowhile()` / `.dountil()` with no iteration bound | addition | Mastra's loop has no cap (`handlers/control-flow.ts:739,901`). `iterationBound` is ours and required explicitly, in [1, 100000]; exceeding it fails the run naming the bound. The bound stops the loop **at runtime by construction** — the budget has one producer and every iteration spends one token — pinned by a structural test, **not by a proof**: the verified properties range over quiescent markings only ([VER-002]), so an endless cycle would violate none of them. A re-entered loop continues `iterationCount` but gets a fresh allowance | refused (M1) |
