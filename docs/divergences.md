# Divergences from Mastra

Every Mastra behaviour this engine does not reproduce is listed here with its classification.
Nothing is skipped silently.

**Classifications.** `abandoned (cause removed)` — the behaviour existed to work around
something this model does not have. `abandoned (defect)` — reproducing it would propagate a
bug. `out of scope` — real behaviour, deliberately not covered by this engine. `replaced` — the
same intent, a different mechanism. `addition` — capability Mastra's engine does not have.

**Statuses.** `proposed` — reasoned from source only. `designed` — the mechanism is observed by
a harness. `refused (M<n>)` — the adapter throws rather than compiling something it would get
wrong, so the divergence is loud at build time. `open (M<n>)` — known wrong, compiled anyway,
not yet fixed; this is the status that must not accumulate. `fixed (M<n>)` — closed in that
milestone.

**Rows 7 onward were established in M1 by reading Mastra's own source** — `@mastra/core@1.67.0`,
recovered from the sourcemaps the package publishes (`scripts/bootstrap-mastra.sh --dist`), so
every citation below resolves to a real line rather than to a planning-time reading. A `refused`
row is a deliberate choice: compiling a wrong answer is worse than refusing to compile.

| # | Mastra behaviour | Classification | Rationale | Status |
|---|---|---|---|---|
| 1 | `.sleep(ms)` resumes with its remaining interval after a suspend | replaced | [CORE-073] restores a marking with every clock fresh, so a restored `.sleep(ms)` re-waits in full. Sound because restores are occasional and `Delayed` is a lower bound; the compiler emits no hard timing on a path that can cross a restore. Unsound for a scheduler that parks and resumes routinely — revisit if Mastra gains one | proposed |
| 2 | Cron-scheduled workflows | out of scope | Declaring `schedule` forces Mastra's evented engine, so a scheduled workflow never reaches this engine | proposed |
| 3 | `.waitForEvent()` | out of scope | Removed upstream; throws `WORKFLOW_WAIT_FOR_EVENT_REMOVED`. Suspend/resume is the mechanism | proposed |
| 4 | Total execution order across independent steps | abandoned (cause removed) | The net produces a partial order. The differential harness requires it to be a *weakening* of Mastra's total order, never a reordering — an unattributed ordering difference is a finding | proposed |
| 5 | `.parallel()` fan-out is unbounded | addition | A `concurrency` annotation compiles to a permit place. Layer 2: a workflow carrying it still runs correctly under `DefaultExecutionEngine`, merely unbounded | proposed |
| 6 | Step timeouts are not virtualized under an injected clock | out of scope (upstream) | `Out.Timeout` still elapses on a real `setTimeout`; only its recovery tokens follow the epoch clock. Reported upstream. Keep timeout values small in timed tests | proposed |
| 7 | `.map()` entries (`{type:'mapping'}`), at top level and as an arm | out of scope | A mapping reads *any* earlier step's result via `ctx.getStepResult(id)` and the run input via `ctx.getInitData()` (`handlers/step.ts:383-384`). `StepRunner.run(stepId, input)` sees only the immediately preceding output, so the data a mapping needs is not reachable. Needs the run-scoped step-result store that also unblocks branch predicates and loop conditions | refused (M1) |
| 8 | `.sleep(fn)` / `.sleepUntil(fn)` — a wait computed per run | out of scope | Mastra stores the entry with `fn` and no `duration`/`date`, resolving the wait at execution time from the previous step's output (`workflow.ts:2085-2099,2135-2148`). Our IR models both as compile-time constants, and `structuralHash` keys the compile cache on that constant. A dynamic wait must be resolved by an action, not emitted as `delayed(ms)` | refused (M1) |
| 9 | `.sleep(ms)` with `ms` above 2147483647 (~24.9 days), including `Infinity` | abandoned (defect) | Mastra sleeps with a bare `setTimeout` (`utils.ts:230-251`); Node resets any delay above the timer maximum, `Infinity` or `NaN` to **1ms**. Compiling `delayed(2592000000)` would wait 30 days where Mastra waits 1ms — reproducing it faithfully means reproducing a bug | refused (M1) |
| 10 | `.sleepUntil(new Date(<unparseable>))` — an Invalid Date | abandoned (defect) | `if (!date)` does not fire for an Invalid Date (a truthy object), so Mastra computes `NaN - Date.now()` and wakes after ~1ms (`handlers/sleep.ts:256-276`). `exact(NaN)` has no meaning in a timed net | refused (M1) |
| 11 | Step-level `retries` and workflow-level `retryConfig.attempts` above 0 | replaced | Mastra runs a step `retries + 1` times with a fixed, non-abortable delay (`default.ts:455-458`); only `MastraNonRetryableError` short-circuits, and a TripWire is retried like any other error. The net models this as a budget place with an inhibitor fallback (M7), which is provable; until that lands, refusing beats silently running a step once | refused (M1) |
| 12 | An empty `.parallel([])` or `.branch([])` | out of scope | Mastra reduces over an empty results array and returns `{status:'success', output:{}}`, continuing (`handlers/control-flow.ts:220,286-295,540,616-624`). Both gadgets require at least one arm to build a join | refused (M1) |
| 13 | `.dowhile()` / `.dountil()` with no iteration bound | addition | **Mastra's loop has no cap of any kind** — a bare `do { body } while (cond)` (`handlers/control-flow.ts:739,901`); a repo-wide grep for `maxIterations` over the recovered source returns nothing. Our `maxIterations` is therefore not parity but a Layer 2 addition, and it is what makes the loop's termination provable. The adapter requires it to be chosen explicitly rather than defaulted, so the bound is never invisible | refused (M1) |
| 14 | `.foreach(step, {concurrency: fn})` — a per-run concurrency resolver | out of scope | `ForeachOptions.concurrency` may be `(context) => number` evaluated per run against the actual input array (`utils.ts:786-796`, called at `handlers/control-flow.ts:983-986`). Lane count is structural in the net — a permit place seeded at compile time — so a per-run count needs a seeded-at-start budget rather than compiled lanes | refused (M1) |
| 15 | A `.foreach()` whose static `concurrency` is mutated between build and execution | out of scope | Mastra deliberately keeps the caller's options object **by reference** so an agentic workflow can mutate `concurrency` after build. We adapt at its value at adapt time. Not refused, because the mutation is undetectable statically — recorded as a real loss | open (M1) |
| 16 | Any `StepFlowEntry` type this engine has not seen | out of scope | A new Mastra entry kind surfaces as a refusal naming the tag, never as a dropped entry | refused (M1) |
| 17 | The record a `.branch()` hands the **next** entry | replaced | Mastra's `getStepOutput` reduces over **all declared arms**, so the next entry sees every arm id as a key with `undefined` for arms that were skipped (`default.ts:1141-1149`), while the block's own output carries only arms that ran and succeeded (`handlers/control-flow.ts:616-624`). Two shapes, both observable: `'b' in input` is true under Mastra and false under us. Our join emits only the arms that ran | **open (M1)** |
| 18 | `.foreach()` stops dispatching after the first non-success item | replaced | `handleNonSuccessResult` calls `killQueue()` — `inFlight -= queue.length(); queue.kill()` (`handlers/control-flow.ts:1087-1090,1128-1141`) — so Mastra performs **zero** further item side effects after one item fails. Our foreach runs every item. Observable and consequential (writes, emails, charges). Structurally an inhibitor on a fault place gating the dispatch transition | **open (M1)** |
| 19 | `suspended`, `bailed`, `paused` and `tripwire` step outcomes | out of scope | A Mastra step handler assigns **six** outcome statuses (`handlers/step.ts:516-529`); `StepOutcome` models two. Unlike rows 7–14 this cannot be refused statically — whether a step calls `ctx.suspend()` is not visible in the IR — so it is the phase's largest silent acceptance. M4 closes it | **open (M1)** |
| 20 | Which error is reported when several `.parallel()` / `.branch()` arms fail | replaced | Mastra reports `results.find(r => r.status === 'failed')` over an array index-aligned with `steps`, i.e. the **lowest arm index** (`handlers/control-flow.ts:267,596`). Our join drains the FIFO head, i.e. the arm that failed **first in time**. Needs the arm index stamped onto the failure arrival | **open (M1)** |
| 21 | A `.branch()` condition that throws | abandoned (defect) | Mastra catches it, logs `WORKFLOW_CONDITION_EVALUATION_FAILED` and returns `null` — the arm is silently skipped and the run continues (`handlers/control-flow.ts:395-498`). We fail the run. A thrown predicate is a bug in the user's condition, and swallowing it turns a bug into a missing branch | **open (M1)** |
| 22 | A `.foreach()` over input that is not an array | out of scope | Mastra has no runtime array check; the only guard is a compile-time conditional type that degrades the parameter to a string literal. Behaviour at run time is whatever `fastq` does with a non-array | **open (M1)** |
| 23 | A nested workflow's internal steps | replaced | `Workflow implements Step`, so a nested workflow arrives as `{type:'step'}` and Mastra runs it opaquely with its own `runId` and its own `stepResults` namespace. We adapt it as one atomic step, which is faithful to that opacity but means its internals are outside every proof. M8 compiles it as an instantiated subnet instead | proposed |
